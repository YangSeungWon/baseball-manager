# 웹 UI — API 계약 & 화면 설계 v0.1

```
api.py    JSON API 레이어 (UI 가 소비하는 유일한 경계면)
season.py (개편) 하루 단위 진행 — play_day()
draft.py  (개편) 지명 단위 진행 — DraftSession
career.py (개편) 오프시즌 단계 분해 — off_rollover / off_fa / off_trades / off_cleanup / draft
```

## 왜 웹인가
설치도 계정도 없이 링크만으로 플레이할 수 있다. 이 장르는 스크린샷 한 장으로
설명이 안 되고 직접 몇 시즌 돌려봐야 재미가 전달되므로, 진입 마찰이 곧 생존이다.
나중에 Electron 으로 감싸 Steam 에 내는 길도 열려 있다.

## API 의 두 가지 규칙

### 1. 엔진 객체는 경계 밖으로 나가지 않는다
모든 반환값은 순수 dict / list / 원시값이다. 검증 완료: 12개 엔드포인트
전부 `json.dumps` 통과, 한 화면당 0.2~10KB.

### 2. UI 가 보는 모든 선수 데이터는 내 팀 스카우트의 눈을 통과한다
진짜 능력치는 이 레이어 밖으로 절대 나가지 않는다. `api.Game._ratings()` 가
유일한 통로이고, 항상 `scouting.report()` 를 거친다.
```json
"ovr": {"lo": 47, "hi": 56, "mid": 52},
"pot": {"lo": 48, "hi": 67, "mid": 57},
"confidence": 41,
"comment": "성실한 선수로 평가된다. 몸이 튼튼하다."
```
게임의 핵심이 '불확실한 정보로 판단하기'이므로, UI 구현자가 실수로 진실을
노출할 수 없도록 **API 경계에서 강제**한다.

## 상태 기계
```
스프링캠프 ──start_season()──▶ 정규시즌 ──(84일)──▶ 포스트시즌
                                  │ advance(n)          │ run_postseason()
                                  ▼                     ▼
                          하루씩 / 끝까지          시즌 정리 (성장·노화·은퇴)
                                                        │ offseason_rollover()
                                                        ▼
   ◀── finish_offseason() ── 드래프트 ◀── resolve_trades() ── 트레이드 ◀── resolve_fa() ── FA 시장
```
사용자가 개입하는 지점은 네 곳이다: **경기 진행 / FA 오퍼 / 트레이드 제안 / 드래프트 지명.**

## 엔드포인트

### 조회
| 메서드 | 화면 | 크기 |
|---|---|---|
| `state()` | 상단 바 (연도·단계·날짜·팀) | 0.2KB |
| `standings()` | 순위표 | 1.3KB |
| `roster(team_id)` | 로스터 (라인업/선발/불펜/벤치/부상자 + 시즌 성적) | 10KB |
| `player(pid)` | 선수 상세 (능력 구간·연도별 기록·커리어·계약·이력) | 1KB |
| `farm(team_id)` | 2군 유망주 | 2.7KB |
| `leaders()` | 리그 리더보드 (타격 7개 / 투구 5개 부문) | 2.2KB |
| `schedule(days)` / `recent_results(n)` | 일정 / 최근 결과 | 0.5KB |
| `finances()` | 재정 (시장규모·수입·예산·연봉총액·계약 목록) | 2.4KB |
| `history(n)` / `records(n)` | 리그 역사 / 통산 기록 | |

### 액션
| 메서드 | 반환 |
|---|---|
| `start_season()` | 새 시즌 시작 |
| `advance(days)` | 진행한 경기 결과 + **내 팀 경기 박스스코어** + 부상 알림 |
| `sim_to_end()` | 정규시즌 끝까지 |
| `run_postseason()` | 챔피언 + 시리즈 결과 |
| `offseason_rollover()` | 은퇴자 / 내 팀 급성장·급락 선수 |
| `free_agents()` | FA 목록 + 예상 요구조건 + 내 예산 여력 |
| `offer(pid, years, aav)` / `cancel_offer(pid)` | 오퍼 등록/취소 |
| `resolve_fa()` | 전체 계약 결과 (내 팀 먼저 정렬) |
| `trade_evaluate(give, get, team)` | 상대 반응 — **수치 대신 말로** |
| `propose_trade(give, get, team)` | 성사 여부 |
| `resolve_trades()` | AI 간 트레이드 처리 후 드래프트로 |
| `draft_board(n)` / `draft_pick(pid)` | 보드 + 지명 |

`trade_evaluate` 는 상대의 정확한 평가액을 주지 않는다.
`accept` / `close`("조금 아쉽습니다. 뭔가 더 얹어 주시죠") / `reject` 세 단계와
상대 팀의 방향성(우승도전/중립/리빌딩)만 노출한다. 정확한 수치를 주면
최적 트레이드를 계산해 버리는 게임이 된다.

## 화면 구성

```
┌─ 상단 바 ────────────────────────────────────────────────────┐
│ 2031 정규시즌 42/84일   부산 코메츠 (중립)   [다음 날] [시즌 끝까지] │
└──────────────────────────────────────────────────────────────┘
 홈 │ 팀 │ 리그 │ 프런트 │ 역사
```

### 홈 (대시보드)
```
┌──────────────────┬──────────────────┬──────────────────┐
│ 오늘의 결과       │ 순위표            │ 알림             │
│ 5 : 3 승          │ 1 수원 52-32     │ ⚠ 김민수 중상    │
│ vs 대구 바이슨    │ 2 부산 48-36 ←   │   45일 결장      │
│ [박스스코어]      │ ...              │                  │
├──────────────────┴──────────────────┴──────────────────┤
│ 최근 8경기  승승패승승패승승        다음 경기: vs 광주 (원정) │
└──────────────────────────────────────────────────────────┘
```

### 팀 › 로스터
그룹별 테이블(라인업 / 선발 / 불펜 / 벤치 / 부상자). 각 행에
`이름 · 나이 · 포지션 · 능력 구간 막대 · 시즌 성적 · 계약`.

**능력 구간은 숫자가 아니라 막대로 그린다.** `47~56` 을 회색 배경 위
파란 구간으로 표시하면 불확실성이 시각적으로 전달된다. 확신도가 낮은
유망주는 막대가 길고, 베테랑은 짧다. 이 한 가지 시각 언어가
스카우팅 시스템 전체를 설명한다.

### 프런트 › FA 시장 (오프시즌에만 활성)
좌: FA 목록(요구 조건 포함) / 우: 내 오퍼 목록 + 예산 여력 게이지.
오퍼는 `연수 × 연평균`으로 넣고, 넣는 즉시 예산 게이지가 줄어든다.
`[시장 마감]` 을 누르면 `resolve_fa()` — **결과는 되돌릴 수 없다.**
AI 팀이 얼마를 부를지는 알 수 없으므로 지르는 판단 자체가 게임이 된다.

### 프런트 › 트레이드
좌: 내 자산(1군 + 팜) / 우: 상대 팀 자산. 가운데에 상대의 반응 한 줄.
상대 팀 방향성(우승도전/리빌딩)이 크게 표시된다 — 리빌딩 팀에
베테랑을 팔려 하면 안 된다는 걸 UI 가 알려줘야 한다.

### 프런트 › 드래프트
```
전체 3순위 · 1라운드 · 내 차례
┌ 보드 (내 스카우트 기준 정렬) ────────────┬ 지명 현황 ──────┐
│ 김현수 18 고졸 SS  잠재력 ▓▓▓▓ 59~75 (12%)│ 1 대전 손민교   │
│ 이동철 21 대졸 SP  잠재력 ▓▓▓  61~68 (67%)│ 2 수원 고광환   │
│ ...                                       │ 3 ← 내 차례     │
└───────────────────────────────────────────┴────────────────┘
```
고졸(넓은 막대·낮은 확신도) vs 대졸(좁은 막대·높은 확신도)의 대비가
화면에서 바로 보인다. 안전한 대졸과 도박인 고졸 중 무엇을 고를 것인가 —
이게 드래프트 화면의 유일한 질문이다.

## 구현 경로

지금 코어는 순수 Python이다. 웹으로 가는 길은 둘이다.

| | 장점 | 단점 |
|---|---|---|
| **코어를 TypeScript로 포팅** | 서버 없음. 정적 호스팅(itch.io/Pages)으로 무료 배포. 오프라인 동작. 즉시 반응. | 약 2,400줄 포팅 작업 |
| **Python을 서버에 유지** | 포팅 불필요 | 호스팅 비용·운영, 매 액션마다 왕복 지연, 오프라인 불가 |

**접근성이 목표라면 TypeScript 포팅**이다. 서버가 없으면 링크만으로 무한히
퍼질 수 있고 비용이 0이다. 세이브는 브라우저 저장소에 둔다.

포팅은 기계적이다. 검증이 끝난 수식과 계수 표(`pa_engine.C`, `game_engine.ADV`,
`development.AGING`, `injury.BASE`, `scouting.SIGMA_*`, `market.MODE_W`)는
언어와 무관하게 그대로 옮겨진다. **이 API 계약이 포팅의 경계선이다** —
`api.py` 가 반환하는 JSON 모양을 고정해 두면, 코어를 갈아끼워도 UI 는 그대로다.

## 남은 것
- **세이브/로드가 없다.** 직렬화 설계 필요 (선수 객체 그래프 + RNG 상태).
- 라인업/로테이션 수동 편집이 없다 (지금은 자동 정렬만).
- 경기 중 감독 개입(대타·번트·투수교체)이 UI 에 없다. 엔진에도 아직 없다.
- 트레이드가 1:1 이상을 지원하지만 AI 응답 로직은 단순 합산이다.
- 다국어 (지금은 한국어 하드코딩).
